# GrowthHub 文档编写与维护规范

版本：1.0

更新日期：2026-10-15

适用范围：GrowthHub 仓库内所有说明、契约、计划、记录和交付文档，以及 AI 代理生成或修改的文档内容。

## 1. 目的与基本原则

文档用于让用户和后续开发者准确理解系统如何运行、为何如此设计、当前做到哪里，以及如何安全地验证和维护。文档应当可以执行、核对和追溯。

- 以仓库当前实现和可复核证据描述“已实现”；计划、设想和建议不能写成已经交付的事实。
- 修改代码、配置、接口、数据库、部署或验证流程时，检查并同步受影响的文档。
- 每项信息尽量只维护一个权威位置，其他文档用相对链接引用，避免复制后逐渐不一致。
- 对不确定、尚未验证或依赖外部条件的内容明确标注，不猜版本、结果、日期或完成状态。
- 文档使用简体中文，保留代码、API、配置项、依赖名称和官方专有名词原文；表达直接、具体。

## 2. 事实来源与冲突处理

文档冲突时按以下顺序核实，不要直接挑选更方便的一种说法：

1. 当前仓库代码、迁移、构建配置和脚本，决定当前实际行为。
2. 实际运行结果、测试输出、部署或恢复记录，证明特定环境中验证过的行为。
3. 当前契约/运维文档，说明预期稳定行为；若与实现不同，应判断是实现缺陷还是文档过期，并修正对应一方。
4. `docs/development-plan.md` 记录经确认的产品基线和阶段目标；它不是当前实现状态的替代品。
5. `docs/progress.md` 记录当前交付状态和未完成事项；历史文档只说明记录时点的事实。

外部产品版本、支持周期、价格、法规或服务行为等可能变化的信息，注明核验日期并链接官方来源。外部资料不能证明本仓库已经实现或通过验收。

## 3. 文档目录与职责

先更新已有权威文档；只有内容有独立读者、生命周期或维护需求时才新增文件。

| 文档 | 唯一职责 |
| --- | --- |
| `README.md` | 项目简介、最短启动/验证入口、关键文档导航；不复制完整运行手册 |
| `docs/development-plan.md` | 人工确认的产品范围、路线、决策基线和验收目标；变更基线时记录日期及变更依据 |
| `docs/progress.md` | 当前状态、已完成范围、实际验证证据、待外部验收项和运行概况 |
| `docs/progress-history-*.md` | 按日期保留阶段性历史记录；不得用旧快照替代当前进度 |
| `docs/architecture.md` | 当前系统边界、模块/技术决策及其理由；重大决策变化注明日期、原因和迁移影响 |
| `docs/api.md` 及专题接口文档 | 当前 HTTP 契约、字段、状态码、约束和交叉链接 |
| `docs/ai-contract.md`、`docs/model-providers.md` | AI 输入输出、生命周期、校验及提供商能力/配置契约 |
| `docs/environment.md` | 开发机环境、安装来源和位置、隔离规则及运维命令；不存秘密 |
| `docs/deployment.md` | 部署、认证、安全、备份和恢复操作手册 |
| `docs/deployment-verification.md` | 部署验收的环境、镜像/版本标识、步骤、结果和限制 |
| `docs/*-summary.md`、`docs/plan-audit.md`、`docs/m3-trial.md` | 对应切片的交付摘要、计划逐项核对或试用记录；明确记录时间及证据范围 |

如需新增专题文档，选择与内容一致的英文小写 kebab-case 文件名，例如 `data-retention.md`，在 README 或相关权威文档中增加导航。避免 `new-doc.md`、`final-v2.md` 等无明确职责的名称。

## 4. 何时必须更新文档

提交前逐项判断。适用的文档应与实现同步交付，不能把“之后补文档”留作默认步骤。

| 改动 | 至少检查 |
| --- | --- |
| 新增/修改/删除功能、用户流程或阶段范围 | `README.md`（用户可见变化）、`docs/progress.md`；若改变确认基线，同时更新 `docs/development-plan.md` |
| API 路径、字段、校验、错误、认证行为 | `docs/api.md` 或对应专题接口契约 |
| 数据实体、迁移、事务、模块边界或依赖选择 | `docs/architecture.md`；若涉及演进/回滚操作，也更新 `docs/deployment.md` |
| AI prompt/schema、提供商配置、预算、重试或数据发送范围 | `docs/ai-contract.md`、`docs/model-providers.md`；用户操作/隐私提示变化时同步 README 或运行手册 |
| 安装、启动、环境变量、端口、脚本、备份/恢复 | `docs/environment.md`、`docs/deployment.md` 或 `.env.example` 注释；禁止将真实值写入文档 |
| 运行验证、里程碑交付、部署或恢复演练 | 更新 `docs/progress.md`；需要保留详细证据时更新对应历史/验收文档 |
| 新增、重命名或删除面向开发者的关键文档 | 更新 `README.md` 导航及相关文档交叉链接 |

仅重构且外部行为、操作方法、数据结构及验证方式均未改变时，可以不改文档；在交付说明中简述判断依据。

## 5. 状态、计划与变更记录

- 计划中的路线调整、优先级、验收门槛和正式计划内容必须由用户确认。AI 可以提出建议或维护已确认内容，不得把建议直接写成正式基线。
- 在 `progress.md` 中使用明确状态，如“已实现”“部分完成”“待验证”“未开始”“不适用”，并写清适用版本/范围。避免只写“完成”而没有对象。
- “已实现”说明功能存在；“已验证”还必须说明验证方式和结果。环境或外部 API 未覆盖时注明限制。
- 更新现状时保留仍有价值的历史结论到 history/summary 文档，避免在当前文档中叠加互相矛盾的旧段落。
- 验收记录至少给出日期、环境或版本、执行方式、结果、失败/跳过项和证据位置。不要把预期结果写成实测结果。
- 架构决策变更说明旧决策、新决策、原因和兼容/迁移影响；已应用迁移不可通过修改旧 Flyway 文件来“同步文档”。

## 6. Markdown 与写作约定

- 使用 UTF-8、简体中文、LF 换行；文件末尾保留一个换行。
- 每个文件以一个一级标题开头；用二级标题组织主题，避免标题层级跳跃。
- 适合比较或字段定义的内容使用表格；步骤使用有序列表；命令使用带语言标记的代码块。
- 命令应可从项目根目录或明确写出的目录复制执行；注明必要前置条件、目标环境和是否会清空数据。
- 文件内引用使用相对链接，且目标存在、大小写一致。涉及路径、字段、环境变量或状态时使用反引号。
- 日期采用 `YYYY-MM-DD`；业务日期和时区规则遵循项目约定 `Asia/Shanghai`。区分业务日期、事件时间及文档更新时间。
- 缩写首次出现时写出中文含义或英文全称。优先使用明确句子，避免“显然”“应该没问题”“完全安全”等无证据判断。
- 文档中的 Mermaid 图应与实际架构一致；复杂逻辑优先同时提供文字说明，图不能替代契约。

## 7. 安全与个人数据

- 不提交或粘贴 `.env` 内容、密码、Token、私钥、Cookie、真实个人日志、数据库转储或可识别的备份路径内容。
- 示例配置只放明显占位符，并与 `.env.example` 保持一致；说明变量用途、默认值和敏感性，不记录真实值。
- 描述数据流时写明个人输入是否发送给外部提供商、何时发送、存储/导出范围及失败处理；不在日志或示例中复制真实输入快照。
- 使用脱敏且明确标注为示例的数据。内部地址或机器路径仅在确有运维价值时记录，并避免暴露无关账号信息。

## 8. 完成文档修改前的核对

1. 重新阅读受影响段落及其链接目标，确认文档职责正确，没有在错误文件复制权威信息。
2. 对照代码、配置、脚本或真实输出，核对版本、路径、参数、字段和状态。
3. 搜索仓库中受影响术语/路径，发现冲突的旧说法后更新或明确标为历史。
4. 检查 Markdown 标题层级、相对链接、代码块、日期、隐私和秘密。
5. 在交付说明中列出更新的文档；若未改文档，说明为何外部行为和操作信息没有变化。

本规范由 `AGENTS.md` 引用；后续如需改变文档管理规则，应同时更新本文件和入口约定。
